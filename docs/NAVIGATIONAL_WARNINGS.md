# 항행경보 API 수집 준비

5단계는 WGS84 기준 지도 연결을 구현했으며 과거 94구역 중 74구역을 표시한다. 현재 동작은 [지도 연동 검증](NAVIGATIONAL_WARNING_MAP.md)을 참고한다. 아래 지도 비활성·측지계 미확인 설명은 이전 단계 및 수집 원본 메타데이터에 관한 기록이다.

4단계 로컬 구현: [단일 Pages 배포 연결·캐시·최초 배포 확인](./NAVIGATIONAL_WARNING_DEPLOYMENT.md). 실제 배포는 하지 않았다. 아래 1~3단계의 ‘배포 미연결’ 설명은 당시 상태이며, 현재 연결 코드는 사용자 반영 전 로컬에 준비된 상태다.

1·2단계에서 수집 기반을 준비했고, 3단계는 기존 항행경보 항목에서 정적 JSON의 목록·원문 상세를 열람한다. 지도 도형·마커·해역 필터·자체 등록 기능은 활성화하지 않는다. 배포 연결은 아직 적용하지 않았다.

## 기존 구조와 변경 경계

기존 지도 정보 목록은 `MapInformationCards`의 `hazard` 항목이다. `mapInformationOrder`/`mapInformationVisibility`의 ID 및 저장 키는 유지한다. App은 `public/data/operational/hazards.geojson`의 빈 독립 원장을 읽고, `hazardPointsFromGeoJson`의 Point 파서를 통해 두 지도 캔버스에 전달한다. 자체 등록 메뉴는 없다. 이 Point 파서에 공식 경보 구역을 넣으면 여러 좌표가 손실되므로 연결하지 않는다. 기존 빈 원장도 변경하지 않는다.

명칭은 `항행경보`이며 카드의 목록 버튼과 기존 하단 진입 버튼에서 같은 열람 패널을 연다. 기존 빈 공간 원장의 0건을 공식 API의 경보 없음으로 해석하지 않는다. 공식 수집 상태는 별도 정적 JSON으로 판단하며 다른 레이어, 저장 상태, 지도 표시 정책은 그대로다.

## 공식 명세와 실제 응답 확인

공식 자료: [공공데이터포털 15057792](https://www.data.go.kr/data/15057792/openapi.do), [API 기본 주소](https://apis.data.go.kr/1192136/NavigationalWarning).

2026-11-21 KST에 포털의 상세기능 HTML과 인증된 HTTP/XML 응답을 대조했다. 기존 서버 환경의 KHOA 인증키로 읽기 전용 검증을 수행했으며 인증키/인증 URL은 기록하지 않았다. 이번 수집기는 별도의 아래 환경변수만 사용한다.

- 현황: `getNavigationalWarningInfo`. `ServiceKey` 필수(대소문자 주의), `date`(YYYYMMDD, 생략 시 당일), `numOfRows`, `pageNo`. 선택 필터 `doc_type`, `app_cat`, `noti_cat`는 현재 사용하지 않는다.
- 상세: `getNavigationalWarningDetailInfo`. `ServiceKey`, `doc_num`, 선택 `area`, `numOfRows`, `pageNo`.
- `header.resultCode=00`과 `body.items.item`, `numOfRows`, `pageNo`, `totalCount`를 검사한다. HTTP 200도 오류 XML일 수 있다.
- 현황 원문 필드: `doc_num`, `doc_type`, `gov_cd`, `noti_cat`, `app_cat`, `title`, `basic`, `content`, `area`.
- 상세 원문 필드: `doc_num`, `area`, `position_nm`, `position`, `position_desc`, `alarm_date`, `alarm_time`, `sea_pos`.

실제 관찰:

|조회 날짜|현황 문서 수|
|---|---:|
|2026-10-01|7|
|2026-11-20|8|
|2026-11-21|7|
|2026-11-22|6|
|date 생략|7 (11월 21일과 같은 문서번호)|

`26-391`의 상세 58구역, `26-392`의 상세 2구역을 정상 XML로 확인했다. 11월 20~22일 합집합은 문서 9건이다. 개별적으로 받은 전체 상세 응답을 수집기에 재입력해 94구역 보존을 확인했다. 응답 원문과 실행 기록은 Git 제외 로컬 `.dev/docs/navigational-warning/`에 있다. 재입력 검증과 한 번에 끝나는 실시간 수집은 구분한다. API/네트워크 중간 오류 시 전체 수집 실패로 처리하며 부분 결과를 정상 데이터로 발행하지 않는다.

`numOfRows=2,pageNo=2,date=20261121`에서도 정상 응답(총 7건 중 `26-396`, `26-397`)을 확인했다. 1단계 연속 실시간 수집에서는 요청 실패가 발생했다. 아래 2단계 검증에서는 재시도로 전체 수집을 완료했다. 초기 정적 JSON은 미수집 상태 그대로 유지하며, 실제 검증 결과는 Git 제외 로컬 경로에만 보관한다. 워크플로의 원격 실행은 수행하지 않았다.

명세와 응답 차이:

- 실제 `area`는 영문자 외에 숫자 `1~58`도 있다. `26-391`에 숫자 `area=1`, `area=2`를 보낸 검증은 실패했고, `area=A` 응답에는 `area=1`이 나왔다. 문자-숫자 대응을 추정하지 않는다. 수집기는 `area`를 생략해 문서 전체 상세를 페이지 순회하고 목록에 나온 모든 구역이 포함됐는지 검사한다.
- 포털의 `noti_cat`/`app_cat` 요청·응답 설명에 명칭 역전이 있고 실제 값도 명세 예시와 다르다. 원문 필드 그대로 보존하고 분류를 재해석하지 않는다.
- 상세의 `alarm_date`/`alarm_time`은 쉼표 나열이며 끝 쉼표가 있다. 일정과 발령일을 합치지 않는다. 현황에 명시적 발령 시각이 없어 `issuedAt=null`이다. `basic`에 적힌 날짜나 문서번호로 발령 시각을 만들지 않는다.

## 좌표와 지역

실제 `position`은 `34-09-41N,128-00-00E` 같은 **위도, 경도 순서의 도분초**이며 여러 쌍이 줄바꿈으로 이어진다. 소수 초도 있다. XML의 `&#xD;`는 줄바꿈으로 해석한다. 원문 문자열과 쌍의 순서를 모두 보존한다. `position_desc`에는 순차 연결한 선내 해역 등이 있다.

94구역 중 92개는 DMS 문법상 해석 가능했고, 1개는 범위를 벗어난 초(`129-28-67E`), 1개는 현재 파서가 해석하지 않는 형식이었다. 잘못된 초를 다음 분으로 올림 보정하지 않는다. 누락/미해석/잘못된 좌표는 각각 `missing`/`unparsed`/`invalid_dms`이며 위치 없이 원문을 보존한다.

공식 문서와 XML만으로 측지계가 확인되지 않았다. 해석 가능한 값도 `datum_unverified`이며 `datum:null`, `geometry:null`이다. **GeoJSON/WGS84로 선언하지 않는다.** 통영·거제 이름만으로 필터하거나 영역의 대표점 한 개를 만들지 않는다. 다음 단계에서 측지계와 구역 의미 확인 후 공식 전체 영역과 관심 해역의 교차 여부를 검토한다. 위치 없는 경보를 목록에서 제공할 정책도 그때 결정한다.

## 누락 방지 조회 전략

`date`를 발령일이라고 단정해 당일 새 문서만 축적하면 안 된다. 실제 11월 21일 조회에는 발행 근거가 11월 5일인 다일 경보가 포함됐고 날짜별 문서 집합이 달랐다. 구역 중 일부는 당일보다 먼저 종료된 일정도 포함되어 있어 현황 조회만으로 개별 구역의 현재 유효성을 확정할 수 없다.

준비 단계 기본은 **KST 어제·오늘·내일 3일을 명시 조회해 합집합**을 만들고, 각 문서의 전체 구역을 수집한다. 날짜별 원문 관찰을 보존한다. 이는 날짜 경계 검증용이며 누락 없는 전체 유효 경보 집합을 보장하는 정책은 아니다. `--dates`로 최대 31일을 지정해 장기 경보/경계일을 대조할 수 있다.

운영 전 제공기관에 `date` 검색 의미, 장기·상시·취소 경보의 포함/해제 규칙, 일정 시간대 및 측지계를 확인해야 한다. 공식 항행경보 원문과 과거·현재·미래 날짜를 대조해 조회 범위를 확정한다. 확인 전에는 `coverage.activeSetCompleteness`와 `dateSemantics`를 `unverified`로 유지하고, 빈 조회 결과를 ‘유효 경보 없음’이나 안전 판정으로 쓰지 않는다. 제공기관 확인 없이 유한한 과거 검색만으로 누락 없음을 주장할 수 없다.

## JSON 및 실패 보존

- `public/data/navigational-warnings/latest.json`: 스키마 v1. `source`, `apiBase`, `lastSuccessfulAt`(UTC ISO), `coverage`, `documents`.
- 문서: `docNum`, `issuedAt:null`, `observations[{queryDate,raw}]`, `areas[{id,raw,coordinates}]`. `raw`는 XML 텍스트의 원래 필드/내용/날짜/시간이다. 같은 문서의 모든 구역을 별도 보존하고 구역 내 모든 좌표 쌍을 유지한다.
- `status.json`: `status`는 `not_collected`/`not_configured`/`success`/`failed`, `lastAttemptAt`, `lastSuccessfulAt`.
- 저장소의 초기 JSON은 미수집(`lastSuccessfulAt:null`)이고 경보 없음 판정이 아니다. 3단계 UI는 이 JSON을 읽어 미수집 상태를 표시한다.
- 페이지 번호/개수/전체 건수의 일관성, 반복 페이지, 구역 누락, 문서 불일치, XML 오류, API 오류를 검사한다. 동일 문서·구역의 동일 원문 중복은 제거하고, 서로 다른 원문이 충돌하면 실패한다. 검증 실패 시 최신 정상 JSON을 교체하지 않는다. `latest.json`은 임시 파일 후 rename으로 교체한다. 오류 시 `status.json`만 실패로 갱신하고 프로세스는 1을 반환한다.
- `dataState`는 미수집/빈 조회 결과/자료 있음, 마지막 시도 실패 여부, 최종 정상 시각, 오래됨(준비 기준 3시간)을 별도로 계산한다. 실패 자료와 오래된 자료의 UI 표현은 다음 단계에서 결정한다. `latest.json`과 `status.json`의 시각이 다르면 최신 snapshot의 정상 시각을 기준으로 한다.
- XML/응답 크기를 제한하고 DTD/외부 엔티티를 거부한다. 응답이나 예외에 인증 URL이 담길 수 있어 원문 오류/stack은 출력하지 않는다. 키가 응답에 포함되면 저장도 거부한다.

## 로컬 실행

Node 24 권장. `npm ci` 후 서버 환경변수 `KHOA_NAV_WARNING_SERVICE_KEY`에 공공데이터포털 키를 설정한다. 디코딩 키 권장, 인코딩 키도 한 번 디코딩한 뒤 URLSearchParams로 인코딩한다. `VITE_`로 만들지 않으며 브라우저 코드, 소스, 명령 인수에 키를 넣지 않는다. 키가 없으면 안내 후 0 종료하고 기존 정상 파일은 유지한다.

PowerShell에서 히스토리/화면에 키를 노출하지 않는 입력 예:

```powershell
$navSecret = Read-Host 'KHOA 항행경보 인증키' -AsSecureString
$env:KHOA_NAV_WARNING_SERVICE_KEY = [System.Net.NetworkCredential]::new('', $navSecret).Password
try {
  node scripts/collect-navigational-warnings.mjs
  # 날짜 범위를 명시할 때:
  # node scripts/collect-navigational-warnings.mjs --dates 20261120,20261121,20261122
} finally {
  Remove-Item Env:KHOA_NAV_WARNING_SERVICE_KEY
  Remove-Variable navSecret
}
```

명령은 정적 JSON을 갱신하므로 기존 정상 파일이 있다면 보존 복사 후 검증한다. 변경 파일을 실수로 배포하지 않는다. 실시간 API 응답 없이 테스트하려면 `node --test src/tests/navigationalWarnings.test.ts`. 전체 검증은 `npm test`, `npm run lint`, `npm run build`, `npm run verify`.

## GitHub Actions 준비 (수집 전용)

[별도 수집 워크플로](../.github/workflows/collect-navigational-warnings.yml)는 UTC 매시 23분(`23 * * * *`, KST도 매시 23분)에 실행하도록 준비했다. GitHub 스케줄 지연 가능성이 있어 정확히 60분 이내 갱신을 보장하지 않는다. main에 등록되어야 스케줄이 활성화된다. 이 작업에서는 commit/push/원격 실행을 하지 않는다.

등록할 Repository Actions Secret: **`KHOA_NAV_WARNING_SERVICE_KEY`**. 기존 조석 `KHOA_SERVICE_KEY`를 변경하거나 수집기에서 암묵적으로 대신 사용하지 않는다.

워크플로는 이전 동일 워크플로/main의 아티팩트를 복구·검증한 뒤 수집하고 결과 JSON/시도 상태만 90일 보관한다. 수집 실패도 이전 정상 snapshot을 아티팩트로 보존한다. 복구에 실패하면 수집을 중단하고 초기 빈 파일로 이전 정상 자료를 덮지 않는다. 아티팩트 만료/삭제 시에는 복구할 정상 자료가 없을 수 있으며 미수집과 구분해 운영 점검해야 한다.

**자동 commit, push, Pages 배포는 없다.** 기존 조석/Pages 워크플로도 변경하지 않는다. UI는 정적 JSON을 읽지만 Pages 빌드가 아티팩트를 가져오는 연결은 다음 배포 단계에서 적용해야 한다. 그 전까지 시간별 수집 아티팩트가 곧 배포된 앱 갱신을 의미하지 않는다.

## 다음 단계에서 결정할 사항

2. 측지계, 좌표 오류 처리, 선·면·반경 구역 해석 및 통영·거제 관심 해역 범위.
3. 위치 없는 경보 목록, 미수집/실패/오래됨 표현과 상세 팝업 및 지도 스타일.
4. 정적 JSON 배포 연결, 수집 이력 보존 및 API 쿼터에 맞춘 운영 호출 수.

## 2단계: 수집 안정화 및 실제 전체 수집 결과

검증 실행은 **2026-11-21 12:11:18~12:12:47 KST**, 조회 범위는 **20261120, 20261121, 20261122**이다. 11월 23일 작업 재개 시 이 결과를 최신 경보라고 재표시하지 않는다. 현재 날짜로 다시 조회하려면 기존 명령의 `--dates`를 생략한다. 불필요한 추가 호출을 피하기 위해 작업 재개 후 동일한 전체 수집을 반복하지 않았다.

|항목|실측|
|---|---:|
|완료 결과|문서 9건, 구역 94개, 누락 검사 통과|
|논리 요청|12회: 현황 3일 + 문서 상세 9회|
|실제 HTTP 요청|16회 (재시도 4회 포함)|
|소요시간|88,991ms (약 89초)|
|확인된 실패|HTTP 503 1회, 요청 타임아웃 3회|
|읽은 HTTP 2xx 응답 본문 누적 바이트|63,580B (HTTP 오류 본문/HTTP 전송량 전체를 뜻하지 않음)|
|대기 간격·백오프 합계|20,987ms|

이전 1단계는 원래 예외를 단일 `request_failed`로 바꿔 과거 실패의 정확한 원인을 소급 확정할 수 없다. 2단계 실행에서는 위 일시적 오류를 구분해 기록했고, 재시도로 모든 현황·상세 조회를 완료했다. 오류의 서버 내부 원인까지 확인한 것은 아니다. 실제 결과/시도 상태/측정값은 `.dev/docs/navigational-warning-stage2/live/` 및 `.dev/docs/navigational-warning-stage2/measurement.json`에 보존한다. 인증키는 포함하지 않는다.

### 요청 정책

- 병렬 호출 없이 순차 요청, 이전 시도 종료 후 최소 1초 간격.
- 요청당 20초 타임아웃, 최초 시도 포함 최대 3회. 재시도 간격 2초·4초 지수 백오프. 전체 실행 요청 상한은 재시도 포함 100회다.
- HTTP 408/429/500/502/503/504, 타임아웃, 허용 목록의 일시적 연결 오류만 재시도한다. HTTP `Retry-After`가 있으면 해당 대기도 지킨다. 30초를 초과하는 대기 요구는 즉시 실패 처리하여 이번 실행의 추가 호출을 중단한다.
- API 코드 `01`(내부 처리 오류), `05`(연결·응답 대기시간 초과)만 제한 재시도한다. 근거: [공공데이터포털 공식 오류 코드](https://www.data.go.kr/tcs/dss/selectErrCodePopupView.do). 인증·파라미터·일일 쿼터·미확인 API 코드, 잘못된 XML/스키마/좌표와 페이지 검증 오류를 무조건 재시도하지 않는다. 좌표 오류는 구역 원문과 오류 상태로 보존하며 수집 전체를 실패시키지는 않는다.
- 오류는 `http_error`+상태 코드, `timeout`, `network_error`+허용된 원인 코드, `api_error`+두 자리 코드, 검증 오류로 구분한다. 외부 예외 메시지·stack·인증 URL·오류 본문은 저장/출력하지 않는다.
- `status.metrics`에 `logicalRequests`, `requests`, `retries`, `responseBytes`, `waitMs`, `failures`, `elapsedMs`를 기록한다. 중간 자료는 정상 JSON으로 게시하지 않는다. 요청 횟수/메트릭은 인증키 없이 재현·점검할 수 있다.

기본 3일 범위가 이번과 같은 9문서 규모라면 무오류 시 12회/실행, 시간별 24회 실행 시 약 288회/일이다. 이번 실행의 16회를 단순 적용하면 384회/일이지만 실제 문서 수와 장애에 따라 달라진다. 쿼터가 확인되기 전 조회 범위를 확대하지 않는다.

### 날짜·상설·장기·취소 경보에 대해 확인한 범위

공식 명세는 `date`를 ‘날짜(default:Sysdate)’라고만 정의하며, 데이터 소개에는 발행일을 이용한 조회라고 적혀 있다. 두 설명과 실측만으로 API의 정확한 검색 조건을 확정할 수 없다.

- `26-391`은 11월 20·21·22일 모두 반복 조회됐고, 상세에는 11월 16~22일의 여러 구역 일정이 있다.
- `26-392`는 같은 3일 모두 조회됐고 상세 일정은 11월 16~30일(15일)에 걸친다. 다일 경보가 포함되는 실제 사례다. 무기한·수개월 경보의 누락 없음을 검증한 것은 아니다.
- 반환 문서 종류는 상설 5건, 비상설·해상훈련·해경훈련·기타 각 1건이다. 공식 `doc_type=1`은 상설을 뜻하지만 수집기는 종류 필터 없이 모두 조회한다. 이번 상설 문서에도 특정 주간 훈련 일정이 있어 ‘상설’을 곧 무기한 유효로 해석하지 않는다.
- `26-393`은 11월 20일만, `26-399`는 20·21일만, `26-409`는 22일만 조회됐다. 날짜에 따른 포함 차이는 확인했다. 그러나 당일 조회된 `26-400`의 개별 일정에는 21일이 없으므로 ‘모든 구역이 해당 날짜에 위험 발생’이라는 해석도 할 수 없다.
- 반환 필드에 구조화된 취소 여부·종료 상태·발령 시각이 없었다. ‘계획 변경’ 제목만으로 이전 경보를 취소하거나, 특정 날짜 조회에서 빠졌다는 이유만으로 종료 처리하지 않는다.

따라서 데이터는 `coverage.activeSetCompleteness='unverified'`, `dateSemantics='unverified'`를 유지하며 `limitations`에 날짜 범위 제한, 상설/취소 포함 범위·일정 시간대·측지계 미확인을 기록한다. 어제의 경보가 포함될 수 있는 3일 합집합은 ‘현재 유효 경보 목록’과 구분해야 한다.

### 좌표 파싱 및 측지계 근거

정상 DMS만 십진수 `coordinates.pairs[{latitude,longitude}]`에 변환한다. `pairCount`로 인식된 쌍 수를 기록하고 순서를 보존한다. 위도 ±90, 경도 ±180, 분·초 0 이상 60 미만을 검사한다. 일부라도 잘못되면 해당 구역의 부분 변환값을 지도 좌표처럼 제공하지 않는다. 원래 `position`과 `position_desc`는 항상 `raw`에 남는다.

이번 94구역은 정상 DMS 문법 92개, `invalid_dms` 1개(`129-28-67E`), `unparsed` 1개(`36-47N, 125-20E`: 초가 없는 도분 형식)다. 유효한 검증용 십진수 쌍은 347개다. 도분 형식에 임의로 초=0을 채우지 않았다.

공식 `position_desc`는 순차 연결한 선내 해역 75구역, 중심 좌표+반경 2~10NM(2.5NM 포함) 19구역이었다. 같은 좌표 개수만 보고 Point/LineString/Polygon을 결정할 수 없으며, 반경 구역도 중심점 하나로 축약하면 안 된다. 이 단계는 도형을 생성하지 않는다.

[공식 API 명세](https://www.data.go.kr/data/15057792/openapi.do)와 [KHOA 항행경보 상황판](https://www.khoa.go.kr/nwb/mainPage.do?lang=ko)의 확인한 페이지에서 이 API 데이터 전체에 적용할 측지계 선언을 찾지 못했다. 국제 항행경보 문서의 일반적인 WGS84 관행만으로 해당 API를 WGS84라고 확정할 수 없다. **측지계는 미확인, 모든 `datum`과 `geometry`는 계속 null**이다. 제공기관 확인 또는 이 데이터에 직접 적용되는 공식 문서가 필요하다.

### 전국 원본과 향후 지역 표시 데이터

현재 수집은 지역명 필터 없이 전국 자료를 보존한다. 이번 **지정한 3일 범위** JSON은 142,880B(약 139.5KiB), gzip 측정은 13,007B(약 12.7KiB)였다. 전국 경보의 모든 과거/상시 자료 총량을 뜻하지 않는다. gzip은 로컬 측정이며 Pages가 실제로 같은 크기로 전송한다는 보장은 없다. 하루 24회 전체 재다운로드를 가정하면 약 3.27MiB/기기(미압축), gzip 기준 약 305KiB/기기이며 HTTP 헤더 등은 제외한다.

다음 단계에서는 전국 원본 JSON을 보존하고, 화면에는 검증된 실제 영역과 현재 지도 표시 범위의 교차 결과를 별도로 계산하는 구조를 권장한다. 전국 자료를 지역명으로 삭제하지 않고, 미확인 위치는 별도 목록 대상으로 보존한다. 통영·거제 고정 경계·필터 좌표·축약 Point는 아직 정하지 않았다.

### 시각과 오래됨

`collectionStartedAt`/`status.lastAttemptAt`는 시도 시작, `lastSuccessfulAt`는 전체 검증 완료, `generatedAt`는 각 JSON 생성 시각이다. 실패 시 snapshot의 최종 정상/생성 시각을 새 시각으로 바꾸지 않고 `status.generatedAt`와 실패 상태만 새로 기록한다. 초기 v1 JSON은 그대로 읽을 수 있으며 새 수집부터 필드가 추가된다.

`freshness.staleAfterSeconds=10800`(3시간)은 준비 단계의 오래됨 기준이다. 앱에서는 최종 정상 시각으로 경과 시간을 계산해야 하며 저장된 `stale:false`를 영구 신뢰하면 안 된다. `dataState`는 정상 0건(`empty_query_result`), 미수집, 수집 실패, 오래됨을 별도 값으로 제공한다. 정상 0건도 전체 유효 경보 없음으로 표현하지 않는다.

## 권장 Pages 연결 설계 — 아직 적용하지 않음

기존 [조석/Pages 워크플로](../.github/workflows/deploy-pages.yml)는 전체 앱을 빌드·배포하며 `concurrency: pages`, `cancel-in-progress: false`를 사용한다. 조석은 이전 정상 아티팩트와 게시된 JSON을 복구하고 검증된 조석 자료가 있어야 배포한다. 항행경보 수집은 별도 `navigational-warning-collection` 그룹이며 배포 권한이 없다. 두 파일 모두 이번 2단계에서는 변경하지 않는다.

권장은 **현재 Pages 워크플로 하나만 배포 주체로 유지**하는 방법이다. 항행경보 수집기에 별도 `deploy-pages`를 붙이거나 데이터 폴더만 배포하면 앱 파일을 잃거나 서로 덮어쓸 수 있다. 전체 사이트 배포는 [GitHub 공식 Pages 워크플로](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)에 맞춰 하나로 모은다.

사용자 승인 후 구현할 연결 순서:

1. 매시 23분 수집은 유지한다. Pages 워크플로만 수집 워크플로의 `workflow_run: completed`를 받도록 확장한다. 실패 수집도 이전 정상 JSON+새 실패 상태를 게시할 수 있지만, 취소/아티팩트 없음/검증 불가 실행은 배포하지 않는다. [공식 이벤트 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)를 따른다.
2. 같은 저장소/main의 허용된 수집 워크플로·schedule/manual 이벤트인지 확인한다. 트리거한 run ID/attempt의 정확한 아티팩트를 임시 폴더에 내려받고 JSON만 검증·복사한다. 아티팩트의 코드나 경로를 실행하지 않는다. 배포 소스는 최신 main으로 고정하고 배포 직전 superseded 검사도 유지한다.
3. 시작 시 이전 정상 항행경보 snapshot을 아티팩트 및 게시된 Pages에서 복구한다. 새 자료가 완전 검증됐을 때만 교체하고, 실패 실행이면 더 최신 정상 자료를 덮지 않는다. 정상 자료가 전혀 없으면 미수집 상태를 명시하고 기존 게시 자료를 빈 기본 파일로 교체하지 않는다. 아티팩트 만료 시 Pages 복구가 필요하다.
4. **항행경보 완료 이벤트에서는 조석 API를 다시 호출하지 않는다.** 현재 조석의 `event != push` 조건을 그대로 확장하면 시간마다 조석 32일 수집까지 반복한다. 해당 이벤트에서는 검증된 조석 snapshot 복구만 수행하도록 명시적으로 분리해야 한다. 기존 일일 조석 일정·push·수동 갱신 정책은 보존한다. 조석 복구/검증 실패 시 전체 사이트 배포를 중단한다.
5. 두 JSON을 전체 앱 `dist`에 포함해 기존 Pages 업로드/배포 단계만 사용한다. 단일 `pages` 그룹에서 직렬화하고 `cancel-in-progress:false`를 유지한다. [공식 동시 실행 제어](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)에 따라 대기 실행이 합쳐질 수 있으므로 오래된 수집 이벤트가 최신 정상 데이터를 되돌리지 않게 시각을 비교한다.
6. 수집 Secret은 **`KHOA_NAV_WARNING_SERVICE_KEY`**만 사용한다. 배포·브라우저에는 필요 없다. 아티팩트 URL을 브라우저에 직접 제공하지 않는다. 브라우저는 Pages의 정적 JSON을 읽는다.

이 방식은 시간별 전체 앱 빌드/배포 비용이 추가된다. 우선 하루 실행 시간과 Actions 사용량을 측정한 뒤 배포를 묶거나 빈도를 조정할지 결정한다. 수집 주기 자체는 1시간을 유지한다. 기존 배포 연결 변경과 최초 실제 배포는 다음 단계의 사용자 승인 대상이다.

### 정적 JSON 캐시 설계

현재 `vite.config.ts`는 항행경보 JSON도 일반 JSON으로 precache하고, 일반 JSON runtime cache는 3초 NetworkFirst/최대 30일이다. 따라서 단순 `fetch(cache:'no-store')` 추가만으로 Service Worker의 예전 응답을 배제할 수 없다. **지금 설정을 수정하지 않았으며, 앱 연결 전에 별도 캐시 정책이 필요하다.**

- 조석과 마찬가지로 항행경보 폴더를 precache에서 제외하고, 일반 JSON보다 앞선 전용 NetworkFirst 또는 NetworkOnly 규칙을 검토한다. 오프라인 자료는 최종 정상 시각/오래됨 표시를 함께 제공한다. API 수집 실패 상태를 정상 0건으로 바꾸지 않는다.
- Pages의 서버 Cache-Control을 임의로 변경할 수 있다고 가정하지 않는다. 배포 후 실제 응답 헤더를 확인하고, 재검증 요청·제한된 갱신 주기와 HTTP ETag를 활용한다. 이번 작업에서는 배포/헤더 변경을 하지 않는다.
- `status.json`과 `latest.json`을 따로 읽으면 HTTP/SW 캐시가 서로 다른 세대를 돌려줄 수 있다. 최종 정상 시각·생성 시각을 대조하고 불일치를 정상 최신으로 표시하지 않는다. 배포 단계에서 검증한 snapshot 해시를 manifest에 넣고 변경되지 않는 세대별 JSON URL을 참조하는 구조가 더 안전하다. 해당 manifest/해시 배포 구조는 이번에는 구현하지 않는다.

## 2단계 최종 로컬 검증

- `npm test`: 192개 통과(기존 180개에서 12개 추가). 항행경보 관련 테스트는 23개다.
- `npm run lint`: 오류 없음, 기존 파일의 경고 11개 유지.
- `npm run build`: TypeScript/Vite/PWA 생성 통과.
- `npm run verify`: 버전·공간데이터·문서 링크·SW 무결성 통과. 항·포구 운영 명칭 154곳도 유지.
- 단계 시작 시 5,715개 로컬 파일 목록/해시와 비교해 수집기·라이브러리·테스트·이 문서 4개만 변경됐고 삭제된 파일은 없었다. 프런트엔드, 기존 데이터, 두 워크플로, 정적 미수집 JSON은 그대로다.
- 실제 수집은 로컬 검증 경로에서만 실행했다. commit, push, GitHub Actions 원격 실행, Pages 배포는 하지 않았다.

## 3단계: 정적 경보 목록·상세 UI

기존 `hazard` 체크박스/저장 키/순서와 지도 전달 구조는 유지한다. 같은 항목에 목록 아이콘을 연결하고, 기존 하단 항행경보 버튼도 같은 패널을 연다. 다른 지도 레이어나 헤더·기능 버튼의 구성은 변경하지 않는다.

- `NavigationalWarningPanel`은 네이티브 하단 dialog이며 목록/상세를 내부에서 전환한다. 목록 복귀 시 스크롤과 선택 카드 초점을 복원하고 닫기/Escape 시 진입 버튼으로 돌아간다. 레이어 관리 안에서 열었다면 해당 관리 화면으로 복귀한다. 패널 내부만 스크롤하며 safe area와 최대 높이 78dvh를 적용한다.
- `navigationalWarningService`는 `BASE_URL` 아래 `data/navigational-warnings/latest.json`과 `status.json`만 `cache:no-store`로 읽는다. 공식 API나 서버 수집기의 XML 파서를 브라우저에 포함하지 않는다. 원본 파일과 수집기/워크플로는 수정하지 않는다.
- 문서는 문서번호로 합치고 구역을 별도로 보존한다. 모든 문서에 해석 가능한 명시적 `issuedAt`이 있을 때만 내림차순 정렬한다. 하나라도 날짜가 없거나 불확실하면 원본 순서를 보존한다. 발행 근거·문서번호·조회 기준일로 발령일을 추정하지 않는다. 현재 실제 수집기의 `issuedAt:null`은 ‘발령일 미제공’이다.
- 상세에는 제목, 문서번호, 제공 날짜(있을 때), 내용 원문/발행 근거, 관련 해도와 구역별 위치 설명·원문 좌표·날짜·시간을 보여준다. 원문 줄바꿈을 유지하고 HTML로 해석하지 않는다. 서로 다른 조회일의 원문이 달라지면 추가 원문도 접어서 열람할 수 있다. 구역은 기본 접힘이다. 좌표 파싱/지도 이동/지도 표시 기능은 없다.
- 미수집, 정상 0건, 자료 있음, 수집 실패+이전 자료 있음/없음, 오래됨, 파일 로드 실패를 구분한다. `latest`만 정상이고 `status`가 실패해도 자료를 숨기지 않고 수집 상태를 확인하지 못했다는 안내를 표시한다. JSON 세대 시각이 다르면 갱신 여부 미확인으로 표시한다.
- 오래됨 기준은 snapshot의 `freshness.staleAfterSeconds`를 사용하며 없으면 `src/config/navigationalWarnings.ts`의 준비 기준 10,800초를 쓴다. 최신·현재 유효함을 보장하지 않는다. 최종 정상 수집 시각만 KST로 변환하고 경보 원문 날짜/시간은 그대로 보존한다.
- 각 파일을 검증하고 HTTP/JSON/스키마 오류를 빈 결과로 바꾸지 않는다. 다시 불러오기와 15초 조회 제한을 제공한다. 기존 PWA precache/runtime cache 정책은 변경하지 않았으므로 `no-store`만으로 SW 캐시를 우회한다고 보장하지 않는다. 수집 시각과 범위 한계를 항상 표시한다.

3단계 테스트는 `src/tests/navigationalWarningUi.test.ts`, `src/tests/navigationalWarning.browser.mjs` 및 기존 지도 정보 회귀 테스트에 포함한다. 브라우저 검증은 실제 컴포넌트에 격리된 JSON 응답을 제공하며 실제 경보를 공개 데이터 파일에 삽입하지 않는다. 320·390·1280px에서 긴 제목/본문, 58구역, 미수집/0건/실패/오래됨, 전환·초점·넘침을 확인한다. 실제 iOS/Android 기기와 스크린리더 실기 검증은 별도 필요하다.

3단계 최종 결과: 단위 테스트 201개 통과, lint 오류 없음(기존 경고 11개), build/verify 통과. Leaflet/Kakao 각각 320·390·1280px 지도 정보 회귀 테스트 통과. 같은 세 너비에서 목록/상세의 axe WCAG 자동 검사 위반 0건, 키보드 이동·Escape·초점 복귀 통과. 2단계에 보존한 실제 응답 9문서/94구역도 UI용 파서로 정상 읽고 오래됨 상태를 확인했다. 수집기·워크플로·공간데이터·초기 미수집 JSON과 기존 저장 키는 변경하지 않았다.

## 개발환경의 실제 과거 자료 미리보기

패널 제목은 목록/상세 모두 `항행경보`다. 미수집 기본 안내는 `아직 수집된 항행경보 자료가 없습니다.`, 보조 안내는 `공식 데이터 연동 후 항행경보를 확인할 수 있습니다.`다. 정상 0건·실패·오래됨·수집 범위 경고는 별도로 유지한다. 패널의 스타일·테두리·닫기 버튼·레이아웃 클래스는 변경하지 않는다.

로컬에 보존된 **2026-11-21 12:12 KST 수집 결과 9문서/94구역**이 실제로 존재한다. `.dev/docs/navigational-warning-stage2/live/`의 검증된 `latest.json`, `status.json`을 바이트 변경 없이 `.dev/fixtures/navigational-warnings/`에 복사했다. 두 경로는 Git 제외 대상이다. 새 경보나 임의의 9개 문서를 생성하지 않았다. 운영 `public/data/navigational-warnings/`는 여전히 미수집 상태다.

PowerShell 실행:

```powershell
$env:BADA_NAV_WARNING_PREVIEW = '1'
npm run dev -- --host 127.0.0.1 --port 5174 --strictPort
# 종료: Ctrl+C 후
Remove-Item Env:BADA_NAV_WARNING_PREVIEW
```

진입 URL: `http://127.0.0.1:5174/?screen=notebook&navWarningPreview=1`. 기존 항행경보 목록 버튼을 누른다. **서버 환경변수와 최초 URL 옵션이 모두 있어야** 미리보기다. 기존 라우터는 URL을 정규화하므로 개발 서버가 최초 요청의 선택을 meta로 전달한다. 라우터는 수정하지 않는다. 새로고침 후에는 위 전체 URL로 다시 진입한다. URL 옵션 없이 진입하면 미리보기 서버에서도 운영 미수집 JSON을 읽는다.

`scripts/navigational-warning-preview.ts`는 Vite `apply:'serve'` 미들웨어다. 고정된 두 개발 fixture만 읽고, 문서/구역 수와 최종 정상 시각·상태를 검증한다. fixture가 없거나 잘못되면 503으로 실패하며 가짜 자료나 운영 자료로 대체하지 않는다. API 호출/키 발급/새 수집은 하지 않는다. 미리보기에는 항상 **`과거 수집 자료 · 개발용 미리보기`**를 표시하며 원래 수집 시각·오래됨·범위 경고도 유지한다.

브라우저의 미리보기 분기는 `import.meta.env.DEV`로 보호된다. 운영 build/preview에는 미들웨어와 진입 meta가 없고 브라우저 분기도 제거된다. `BADA_` 환경변수는 Vite 브라우저 노출 prefix가 아니며 키 값은 브라우저에 전달하지 않는다. 미리보기를 종료할 때 환경변수를 지우고 일반 개발 서버를 사용한다.

fixture가 없는 다른 체크아웃에서는 먼저 동일한 검증 완료 원본 두 파일을 위 개발 fixture 폴더에 준비해야 한다. 원본이 없다면 미리보기는 사용할 수 없으며 임의 생성하지 않는다. 운영 폴더에 복사하지 않는다.

운영 산출물 제외 확인(환경변수를 켠 상태로 build해도 비활성):

```powershell
npm run build
node scripts/verify-navigational-warning-preview.mjs
npm run verify
```

전용 검사는 dist 전체에서 개발 진입 옵션/meta/경로/배너, fixture 원문 제목, 개발 폴더 포함 여부를 검사하고 운영 두 JSON이 원본과 같은지도 확인한다. 실제 9문서/94구역을 모두 순회하는 브라우저 검증은 `src/tests/navigationalWarningPreview.browser.mjs`다. 개발 fixture가 없는 CI에서는 실제 자료 단위 테스트만 명시적으로 skip하며, 잘못된 자료/비활성화 게이트 테스트는 계속 실행한다.

이번 검증 결과: 단위 테스트 204개 통과(skip 없음), lint 기존 경고 11개 외 오류 없음, build/verify 및 운영 산출물 제외 검사 통과. 실제 자료는 390·1280px에서 문서 9건·구역 94개를 모두 열람했고 원문 줄바꿈·좌표·날짜·시간·관련해도·접기/펼치기·복귀/닫기를 확인했다. 실제 App의 미리보기 진입도 Leaflet/Kakao 390px에서 확인했다. 일반 상태 UI/접근성 검사는 320·390·1280px, 지도 정보 회귀는 두 엔진/세 너비에서 통과했다(다운로드 시간 초과가 있던 Kakao 1280px는 단독 재실행 통과). 운영 빌드 실행에서도 미리보기 URL 옵션/위조 meta가 무시되고 운영 미수집 자료만 읽는 것을 확인했다.

## 항행경보 UI 간소화

목록에는 최종 정상 수집 시각·수집 건수·짧은 상태만 남긴다. 미수집/정상 0건/수집 실패/이전 정상 자료/오래됨/개발용 미리보기를 구분한다. 조회 기준일 나열과 범위 보장 설명, 미수집 보조 설명은 목록에서 제거하고 기존 `꼬미의 조타실 → 이용 안내 → 항행경보 안내`에서 설명한다.

카드는 문서번호·제목·최대 2줄 본문 미리보기이며 발령일이 없으면 안내 문구를 생략한다. 카드 전체 클릭과 기존 색상·테두리·모서리는 유지한다. 상세 순서는 제목/문서번호 → 내용 원문 → 기본 접힘 구역 → 기본 접힘 ‘추가 정보’다. 발행 근거·공식 제공 날짜·구역별 관련 해도·다른 조회일 원문·출처는 추가 정보에 보존한다. 원문 좌표·날짜·시간과 줄바꿈은 변경하지 않는다.

조타실 안내는 **현재 파일의 `23 * * * *`(매시간 23분)**과 앱 자동 갱신 연결 준비 상태를 정확히 설명한다. 07:17·13:17 일정은 적용하거나 안내하지 않는다. 공식 자료, 한국시간 어제/오늘/내일 조회, 상설·취소 처리 미확인 및 전체 유효 경보 포함을 보장하지 않음, 공식 항행안전정보를 대체하지 않음과 공식 출처를 제공한다. 새 메뉴는 만들지 않는다. UI용 `briefMessage`는 표시 문자열일 뿐 수집 JSON 구조나 수집 정책을 변경하지 않는다.

수집기·원본/운영 JSON·두 워크플로·hazard 저장 키·지도 렌더링·개발용 미리보기 격리는 그대로 유지한다. 일반 상태와 조타실의 브라우저 검증 및 실제 과거 9문서/94구역 미리보기를 320·390·1280px에서 확인한다. 안내의 수집 주기는 현재 워크플로와 대조하는 단위 테스트로 드리프트를 검사한다.

간소화 검증 결과: 단위 테스트 205개 통과, lint 기존 경고 11개 외 오류 없음, build/verify 및 개발 미리보기 운영 산출물 제외 검사 통과. 상태별 UI·조타실·원문과 추가 정보 순서·접기/펼치기·접근성 자동 검사를 세 너비에서 통과했다. 실제 과거 9문서/94구역도 세 너비에서 확인했다. 390px의 두 지도 엔진 회귀는 정상 모드로 통과했다(일반 개발 서버 초기 로드 시간 초과 후 준비된 별도 개발 서버에서 단독 재실행). 수집기·JSON·워크플로·App/지도 원본과 기존 미리보기 구현 파일은 변경하지 않았다.
